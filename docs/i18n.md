# Translation workflow (i18n)

Weblate pushes translation commits to the `i18n` branch, never directly to
`main`. This keeps the machine-generated locale churn out of the feature
history and shrinks every future upstream sync to at most the locale files.

## Branch layout

- `main` — feature development. Locale files change here only when a feature
  adds or removes keys in `values/strings.xml` (the source of truth).
- `i18n` — Weblate target. Rebased onto `main` whenever it drifts.
- `weblate-main` — legacy remote branch from the pre-split days; do not use.

## Adding user-visible strings

1. Add the key to `manager/app/src/main/res/values/strings.xml` in the same
   commit as the feature that uses it.
2. Do not hand-edit the per-locale files. Leave them to Weblate; the build
   falls back to the default locale for anything not yet translated.
3. Do not cherry-pick upstream Weblate commits. Their key set diverges from
   this fork's; take the English key additions from the feature commit
   instead, then let Weblate fill the locales.

## Ordering rule

When syncing an upstream manager feature, land the feature and its new
English keys first, push, then merge `main` into `i18n` so Weblate sees the
new keys. Doing it in the other order leaves `i18n` referencing keys that do
not exist yet.
